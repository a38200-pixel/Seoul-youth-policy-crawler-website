# 개발 일지

서울 청년정책 마감 D-Day 알리미의 개발 과정 기록. 시간 순서이며 각 항목은 **문제 → 한 일 → 결과 → 남은 의문** 형식이다.

- 수치는 확인된 실행 결과만 적었다. 확인하지 못한 값은 `TODO(확인 필요)`, 근거가 약한 해석은 **가설**/**추정**으로 표시했다.
- 항목별 정확한 날짜를 기록해 두지 않은 곳은 `TODO(확인 필요)` 로 남겼다(실제 코드 변경 시점은 `git log` 참고).

## 1. 크롤링 구조

**문제**

- 청년몽땅정보통에는 접속 대기열(WebGate) 스크립트가 있어 `requests` 로는 목록이 나오지 않는다.
- 전체 공고(9,254건) 중 모집중·모집예정·상시만 필요하다.

**한 일**

- Selenium 브라우저로 목록 URL 에 접속해 `.category-feed` 가 뜰 때까지 `WebDriverWait` 로 기다리고, 같은 드라이버 세션으로 계속 이동한다.
- 목록 URL 은 지도 관련 파라미터를 뺀 최소형으로 만든다(`selectors.list_url`): `key`, `pageIndex`, `orderBy`, `recordCountPerPage=24`, 모집상태 `sc_rcritCurentSitu` 3개(상시/모집중/모집예정). 한 페이지 24건, `pageIndex` 를 바꿔 이동하고 항목이 0개인 페이지에서 끝낸다(상한 300페이지).
- 요소를 못 찾으면 `None` + 경고 로그로 처리하고 셀렉터는 `selectors.py` 한 곳에만 둔다.
- 목록 → 상세 → `make_row` → `upsert_program` 순으로 저장하고, 테스트는 `samples/` 의 HTML 파일로만(네트워크 없이) 한다.

**결과**

- 목록에 보이는 "전체 N건" 이 매일 달라진다: 2026-10-01 에 1514건, 2026-10-03 에 1503건.
- 헤드리스(`--headless=new`)에서도 대기열을 통과해 목록이 읽히는 것을 확인했다. 브라우저 옵션은 `--window-size=1920,1080`, `--lang=ko-KR`(언어 설정이며 탐지 회피가 아님)만 쓰고 User-Agent 위장 등 우회는 쓰지 않는다.

**남은 의문**

- 10-03 일일 실행 후 활성 1502건 = 사이트 표기 1503건 − 제외 1건(게시요청 가이드). 목록 상태별은 모집중 422 / 모집예정 12 / 상시 1069, 상세는 오늘 받은 434건을 건너뜀.
- 사이트 마크업이 바뀌면 셀렉터가 깨진다. 지금은 0건이면 DB 를 건드리지 않고 종료 코드 2 로 끝나게 해 둔 것이 전부다.

## 2. 신청기간 분류 설계

**문제**

- 신청기간 원문은 "2026-09-29 ~ 2026-10-09\n 00 : 00" 처럼 공백·줄바꿈·시각이 섞여 있고, "상시 [ 선착순 마감 ]", "~ 2026-10-08 00 : 00", "2026-09-20 ~ 00 : 00 [ 선착순 마감 ]" 같은 불완전한 형태도 있다.
- 상세 페이지의 **진행일정**에도 날짜가 있어서, 이를 마감일로 쓰면 D-Day 가 틀어진다.

**한 일**

- `classify_period` 가 `(period_type, start, end)` 를 돌려준다. 판정 순서는 dated → end_only → open → always → unknown.
  - `dated`: 날짜 범위가 있음 / `end_only`: "~ YYYY-MM-DD" 로 시작해 시작일이 없음 / `open`: 마감일 미정 / `always`: "상시"로 시작 / `unknown`: 해석 불가(경고 로그).
- `start_date`/`end_date` 는 **신청기간에서만** 만들고 진행일정(`schedule_text`)은 표시용으로만 저장한다. 시각은 무시하고 날짜만 쓴다. 기준 시간대는 Asia/Seoul.
- 처음에는 `open` 이 없어 이런 글이 `unknown` 이었다. 실제 사례(상세 샘플)를 보고 `open` 을 분리해, "해석 불가"와 "마감일이 아직 없을 뿐인 글"을 구분했다. `open` 이 아닌 해석 불가 문자열("~"만 있음, "~ 추후 공지", 빈 문자열)은 계속 `unknown` + WARNING 이다.
- 규칙을 바꾼 뒤 저장된 행에 적용하는 `--reclassify`(사이트 접속 없음, 변경 이벤트 만들지 않음)를 추가했다.

**결과**

- 분류별 테스트(`test_normalizer.py`, `test_record.py`)로 진행일정이 `end_date` 로 새지 않음을 고정했다.

**남은 의문**

- 새로운 형태의 신청기간 문구가 나오면 `unknown` 으로 떨어진다. 실행 요약에 `unknown` 원문을 전부 출력하게 해 두었으므로 그때 규칙을 추가한다.

## 3. 변경 감지 설계와 첫 실데이터 검증(10-02 → 10-03)

**문제**

- 공고가 연장·단축되거나, 상태가 바뀌거나, 목록에서 사라져도 그 이력이 남지 않았다.
- 사라진 이유가 "마감이 지나서"인지 "마감 전에 내려간 것"인지 구분하고 싶었다.

**한 일**

- `program_changes` 에 이벤트를 기록한다: `extended`, `shortened`, `period_changed`, `status_changed`, `deactivated`(reason: `expired`/`early`), `reactivated`. upsert·비활성화와 같은 트랜잭션에서 이전 값과 비교하므로 같은 값으로 재실행하면 이벤트가 생기지 않는다.
- NEW 는 이벤트로 저장하지 않고 `first_seen_at` 으로 계산한다(`db.is_new`, 기준일 `BASELINE_DATE = 2026-10-01` 보다 뒤이고 7일 이내). 기준일에 처음 적재한 행은 NEW 가 아니다.
- 연장과 단축은 대칭으로 따로 기록한다(이전·새 마감일이 모두 있을 때만).

**결과 (10-02 → 10-03 실데이터)**

- 비활성화 37건 = 만료(`expired`) 24건 + 마감일 전에 내려감(`early`) 13건.
  - 만료 24건은 10-02 에 D-Day 였던 24건과 정확히 일치했다.
  - 마감일 전에 내려간 13건은 마감일 미정 4건 + 상시 9건이며 ID 는 64695~64727 이다.
- 상태 변경 2건(74544, 74566: 모집중 → 모집예정). 사이트가 자기 표기를 정정한 것으로 보인다(**추정**).
- 연장·단축 이벤트는 이 기간에 관찰되지 않았다. 표본이 하루뿐이라 검출기가 맞는지를 이 데이터로는 확인하지 못했다.
- 같은 날 재실행에서 변경 이벤트 0건 → 멱등성 확인(자세한 실행 수치는 4번 항목).

**남은 의문**

- **가설(검증 전)**: 사이트가 상시 게시글을 등록 약 1년 뒤에 숨기는 것으로 보인다. 근거는 활성 상시의 최소 ID 가 64782 라는 점뿐이다. 다음 날 새로 내려가는 상시 건의 ID 가 64782~64820 부근이면 지지, 벗어나면 폐기한다. → 10-04 자료를 더해 원인을 경쟁 가설 2개로 다시 정리했다(12번 항목). 10-04 수집에서는 상시가 내려간 건이 없어 이 예측은 아직 검증되지 않았다.
- **가설(표본 작음)**: 신청기간이 불완전한 글(시작일만 있거나 종료일만 있는 글)은 1~2일 안에 사라지는 경향이 있다(지금까지 9건 중 9건).
- 연장·단축은 실제 사례가 쌓일 때까지 `TODO(확인 필요)`.

## 4. 일일 수집 정책(--daily) 설계

**문제**

- 매일 목록 전체(약 1,500건)의 상세 페이지를 모두 받으면 사이트 부담이 크고 오래 걸린다.
- 부분 수집을 완전 수집으로 오인하면 안 본 공고가 전부 비활성이 된다.

**한 일**

- `--daily` 는 목록은 전체를 읽고, 상세는 다음 대상만 받는다(중복 제거, 앞 구분이 우선): (a) 신규·상세 미수신, (b) dated/end_only/open/unknown 은 매일, (c) 목록 상태가 바뀐 행, (d) 7일 이상 지난 상시를 오래된 순으로 최대 200건.
- 상세를 받은 시각은 `detail_fetched_at` 에 기록하고, 오늘(Asia/Seoul) 이미 받은 행은 다시 요청하지 않는다. `last_seen_at` 은 목록만 본 upsert 도 갱신하므로 판정에 쓰지 않는다(초기 구현의 버그를 고친 부분).
- 안전장치: 목록을 끝까지 정상으로 읽은 실행에서만 `deactivate_unseen` 호출 / 수집 건수가 직전 활성 건수의 50% 미만이면 호출하지 않고 경고 / 상세 연속 10건 실패 시 중단(종료 코드 4, 비활성 처리 안 함) / `--max-pages`·`--detail-limit` 은 부분 실행으로 취급.
- 사이트 요청 없이 대상 건수를 미리 보는 `--daily-plan`(DB 읽기 전용)을 추가했다.

**결과**

- 10-03 일일 실행: 878.5초, 상세 요청 435건, 실패·WARNING·ERROR 0건.
- 같은 날 재실행(상세 건너뜀)은 154.5초와 137.4초가 걸렸고 변경 이벤트는 0건이었다.

**남은 의문**

- 상시 갱신 대상은 아직 적재 초기라 대부분 `detail_fetched_at` 이 최근이어서, 7일 주기·200건 상한이 실제로 어떻게 동작하는지는 며칠 더 운영해 봐야 안다. `TODO(확인 필요)`
- 기존 DB 는 `detail_fetched_at` 을 백필하지 않아 첫 실행에서 상세를 한 번 다시 받는다(의도한 동작).

## 5. 표시 규칙(날짜 우선, 상시-기타 기본 숨김)

**문제**

- 사이트의 모집상태와 신청기간 날짜가 어긋나는 경우가 있다(시작일이 미래인데 사이트는 모집중 등).
- 상시 공고 중 분야가 비어 있는 것들은 목록을 어지럽힌다.

**한 일**

- `backend/service/display.py` 에 DB 접근 없는 순수 함수로 구현했다(`compute_display`, `sort_programs`, `badges`).
- **날짜가 사이트 상태보다 우선**한다: 시작일이 미래면 사이트가 모집중이라고 해도 "모집예정(시작 D-n)" 으로 표시한다. 마감이 지난 행은 `expired` 로 보고 목록에서 뺀다.
- 정렬은 모집중(D-Day 순) → 모집예정(시작일 순) → 마감일 미정 → 상시 → 상시-기타 → 확인 필요. 분야가 없는 상시는 `상시-기타` 그룹으로 두고 기본 목록에서 숨긴다.
- 배지: NEW, 연장, 단축, 기간 변경, 상태 변경, 재등록(최근 7일 이벤트).
- 읽기 전용 FastAPI(`backend/api/`)가 이 함수를 그대로 써서 `/api/programs` 등을 제공한다. DB 는 요청마다 `mode=ro` 로 연다.

**결과 (10-02 수집분(활성 1527건) 기준 DB 표시 검증)**

- 모집중 435 / 모집예정 12 / 마감일 미정 4 / 상시 928 / 상시-기타 148, 오늘 마감(D-Day) 24건.

**남은 의문**

- 모집상태가 모집예정인 `end_only` 는 시작일을 몰라 "시작 D-n" 을 만들 수 없다. 화면에서 어떻게 보여 줄지는 UI 단계에서 정한다. `TODO(확인 필요)`

## 6. 자동 수집 설정 중 겪은 문제

**문제**

- Windows 작업 스케줄러에 `scripts/run_daily.bat` 을 연결했더니 작업 결과가 `3221225477`(0xC0000005, 접근 위반)으로 나왔다.
- Windows 이벤트 로그상 크래시한 프로그램은 파이썬이 아니라 `cmd.exe`(오류 모듈 `ntdll.dll`)였다.
- 같은 `.bat` 은 일반 터미널에서는 정상 동작했다.
- 이 시도에서 크롤 로그에는 새 실행이 기록되지 않았다(파이썬이 시작되기도 전에 실패한 것으로 보인다).

**한 일**

- 작업 동작을 `.bat` 대신 콘다 환경의 `python.exe` 를 직접 호출하도록 바꿨다(`-m backend.crawler.crawl --daily --headless`).
- 작업 설정: 이름 `SeoulYouthDaily`, 매일 07:00, 놓친 실행은 가능한 한 빨리 시작, 제한 시간 2시간.

**결과**

- 수동 시작 시 `LastTaskResult` 0, 크롤 로그 소요 137.4초, 다음 실행 예정 2026-10-04 07:00 으로 확인했다.
- `scripts/run_daily.bat` 은 수동 실행용으로만 남기고 스케줄러는 쓰지 않는다.

**남은 의문**

- `.bat` 경유 시 `cmd.exe` 가 크래시한 **원인은 규명하지 못했다(원인 미상)**. python.exe 직접 호출로 우회한 것이다.
- 스케줄러 작업의 시작 위치(작업 디렉터리)는 프로젝트 루트(저장소 최상위 폴더)다(`-m backend.crawler.crawl` 은 프로젝트 루트에서 실행해야 한다).
- PC 가 켜져 있고 로그인된 상태여야 실행된다. PC 가 켜져 있지 않거나 로그인되지 않은 날은 실행되지 않아 수집 공백이 생길 수 있다.
- 07:00 자동 실행의 연속 성공 이력은 아직 쌓이지 않았다(수동 시작 1회 확인). `TODO(확인 필요)`

## 8. 시안의 가정과 실데이터의 차이

**문제**

- 시안에는 "오늘 마감 24건", "마감일 미정 4건"이 들어 있었다. 이 값은 **10-02 수집분** 기준이었다.
- 10-03 수집 뒤의 실데이터는 달랐다: 오늘 마감 **2건**(10-03 은 토요일), 마감일 미정 **0건**. 날짜별로는 10-04(일) 5건, 10-05(월) 24건이었다.
- 날짜별 마감 건수가 10월 기준 1~28건이라, 달력의 점 하나(있다/없다)로는 건수 차이를 구분할 수 없었다.

**한 일**

- "오늘 마감"과 "마감일 미정" 섹션은 **0건이면 숨기도록** 했다.
- 달력의 점을 건수에 따라 **3단계**(1~5건 / 6~15건 / 16건 이상)로 바꿨다. 기준은 상수 한 곳(`src/lib/calendar.ts`)에 둔다. 색만으로 전달하지 않도록 날짜 버튼의 `aria-label`·`title` 에도 건수를 넣었다.

**결과**

- 10-03 개발용 복사본 기준으로 화면의 오늘 마감은 2건, 마감일 미정 섹션은 나타나지 않았다.

**남은 의문**

- **가설**: 평일에 마감이 몰린다. 근거는 10-03(토) 2건·10-04(일) 5건에 비해 10-05(월) 24건이라는 점뿐이다. 표본이 하루치(수집 하루)라서 검증하지 못했다.

## 9. 달력 날짜 필터를 API 에 먼저 추가

**문제**

- 달력에서 날짜를 누르면 그날 마감 공고 목록으로 바꿔야 한다. 화면에서 목록을 직접 거르면 달력의 건수와 목록의 건수가 어긋날 수 있다.

**한 일**

- 프런트보다 API 를 먼저 만들었다: `/api/programs?date=YYYY-MM-DD`(그 날짜가 `end_date` 인 공고만)와 `/api/calendar?month=YYYY-MM`(날짜별 마감 건수).
- 두 엔드포인트가 같은 판정 함수(`display.deadline_on`)를 쓰게 해서, **같은 필터(q·category 포함)에서 `/api/programs?date=X` 의 total 과 `/api/calendar` 의 X 날짜 count 가 항상 같다**는 불변식을 테스트로 고정했다.

**결과 (개발용 복사본 DB, 기준일 2026-10-03 고정)**

- `/api/calendar?month=2026-10` 의 건수 합계 312건이 별도 SQL 로 센 값과 일치했다. 점이 있는 29일 모두 날짜별로 일치했다.
- `/api/programs?date=2026-10-06` 의 total 26건과 달력의 10-06 건수 26건이 같았다.

**남은 의문**

- 만료된 공고는 숨기는 규칙이라 과거 날짜는 항상 0건이다. 지난 마감을 돌아보는 기능은 지금 없다.

## 10. React 구현과 한계, 그리고 API 보강으로 해결한 것

**문제**

- 시안 D 를 실제 화면으로 만들어야 했다. 처음 구현에서는 API 가 주지 않는 정보를 화면이 우회해서 만들었다.
  - 분야 칩: 분야 목록이 없어서 `tab=all` 전체(200건씩 여러 번)를 읽어 `category` 값을 모았다.
  - 마감일 미정: 개수 필드가 없어서 목록 끝 50건을 훑어 `group=open` 을 찾았다.
  - 변경 문구: `/api/changes` 에 `end_date` 가 없어서 "마감일 전에 내려감"과 "게시 종료"를 구분하지 못했다.

**한 일**

- Vite + React + TypeScript 로 구현했다. 라우터·상태관리·CSS 프레임워크·차트 라이브러리는 쓰지 않았고, 추가 의존성은 테스트용 Vitest(+ jsdom, @testing-library/react)뿐이다. D-Day 는 서버가 준 `d_day_label`·`today` 만 쓴다(브라우저 시계로 계산하지 않음).
- 위 우회를 API 보강으로 해결했다:
  - `/api/meta` 에 `categories`(이름·건수) 추가 → 칩은 meta 에서 온다(최초 요청 1번).
  - `/api/programs` 에 `group` 필터와 `group_counts` 추가 → 마감일 미정은 개수(`group_counts.open`)와 항목(`group=open`)으로 가져온다.
  - `/api/changes` 항목에 `end_date`·`period_type` 추가 → 내려감 문구를 `reason`·`end_date` 로 구분한다(만료 → "마감됨", 마감일 전 → "마감일 전에 목록에서 내려감", 마감일 없음 → "게시 종료").
- "곧 마감" 목록은 `group=recruiting` 으로 한정하지 않고, `tab=deadline` 정렬에서 `[오늘 마감 건수, 전체 − 마감일 미정 건수)` 구간만 읽는다. `recruiting` 으로 한정하면 모집예정(`upcoming`) 공고가 화면에서 사라지기 때문이다.
- 관련 커밋: `5bbb3c2`(React 화면 추가), `1183ce8`(API 보강), `3444cb1`(프런트 우회 코드 교체).

**결과**

- 2026-10-03 에 실행한 테스트: `pytest -q` 427 passed, `npm test`(`frontend/`) 테스트 파일 4개 46 passed. `npm run build` 성공.
- 개발용 복사본으로 브라우저에서 확인했다: 탭 건수 마감 임박 434 / 상시 922 / 기타 146 / 최근 변경 72, 분야 칩 14개, 날짜 선택 시 "10월 6일 (화) 마감 26건", 최근 변경 탭의 내려감 37건 중 "마감됨" 24건·"게시 종료" 13건.

**남은 의문 (한계)**

- 캘린더 `.ics` 내보내기는 구현하지 않았다(버튼은 비활성).
- `/api/changes` 는 서버 페이지네이션이 없어 화면에서 50건씩 나눠 보여 준다.
- 프런트 린트(oxlint) 경고 2건(`frontend/src/api/hooks.ts`)이 남아 있다.
- 모바일 실기기, 스크린리더 실사용, 글자 대비의 도구 측정은 하지 않았다.
- 연장·단축·기간 변경·다시 게시됨 이벤트와 '마감일 미정' 섹션은 개발 복사본에 해당 데이터가 없어 실데이터로 화면을 확인하지 못했다(단위·모의 데이터 테스트로만 확인).
- '확인 필요'(`unknown`) 공고는 어느 탭에도 나오지 않는다(화면이 `tab=all` 을 쓰지 않음). 복사본에서는 0건이었다.

## 12. 첫 예약 자동 실행(10-04 07:00)과 내려간 공고의 규칙

**문제**
